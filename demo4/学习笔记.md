# demo4 学习笔记

## 回答问题

- <code>新增“先总结需求”动作</code>：可以增加 summarize_requirement。需要同时修改 system prompt 中的动作白名单和规则，在 state 中加入 requirement_summary，在 build_state_message 中展示该字段，并在 run_task_agent 中增加对应分支。模型选择该动作时必须返回简短需求摘要，程序校验后写入 state，再继续决定路径和内容。只改 prompt 而不改程序分支会触发“未知动作”错误。

- <code>改动状态结构并观察稳定性</code>：可以增加 content_format、validated 或 retry_count。状态字段只有在三个位置保持一致才有意义：初始化、写回和发送给模型。字段过少会丢失关键事实，字段过多会增加 prompt 噪音和状态不一致风险。练习时应记录每一步 action 和 state，检查模型是否重复执行已经完成的步骤。

- <code>比较先规划后执行与直接生成</code>：直接生成只需一次模型调用，延迟和成本更低，适合简单、低风险任务；先规划后执行需要多轮调用，但每一步有明确 action、状态和错误检查，更适合多步骤或有副作用的任务。评价时应比较成功率、调用次数、token、错误可定位性和任务可审计性，而不只比较最终文字。

## 总结

demo4 将任务推进显式化：模型只能从 decide_path、draft_content、create_file 和 finish 中选择动作，程序维护结构化 state 并执行分支。它体现了“模型负责决策，程序负责执行”的边界。Planning 提高可控性和审计性，但也增加调用次数，并可能限制开放任务的灵活性。
